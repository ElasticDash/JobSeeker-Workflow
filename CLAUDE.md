# Resume pipeline house rules

These were saved preferences in claude.ai and applied automatically there. Claude Code only sees them from this file.

## Writing
- Never use em dashes in any output.

## Candidate resumes
- Profile template: "[title] with [N] years of experience in [focus area]. Highly experienced in [past fields covered]. Passionate about [a larger personal goal]. [traits important for the target role] who can [short description of capability]." Sentence 1 opens with the title itself, no soft-skill prefix ("Technical program manager with 4 years...", not "Structured technical program manager..."). This overrides the "[soft skill] [title]" opener still written in ideal-candidate, cv-pass-gap-fix and humanizer-us-resume.
- Profile: summarize experience only, no metrics or achievement numbers. Avoid overused resume terms (e.g. "detail-oriented"); when the JD names attention to detail, use a fresher phrase like "a sharp eye for detail".
- Profile years: a plain whole number, no hedges like "nearly". Don't imply all the years were in the target title when some were in another function.
- The title in the headline under the name and the title in the Profile must match.
- Bullets: don't repeat the same opening verb across experiences. Internships use weaker verbs ("managed", not "led").
- Experience entries ordered most recent first.
- Skills: label the last line of tail items "Others:", not "Also:".
- Every education entry carries dates; date ranges use an en dash ("Jun 2025 – Sep 2025"), not "to".
- When the job location differs from the candidate's location, put "(able to relocate)" right after the location in the header — unless the candidate's profile states "Willing to relocate: No", in which case never add it (see Screening and checks below for what that also means for whether the job is suitable at all).
- Ideal-candidate versions stay credible: don't track the JD wording too closely, no unrealistic figures.

## Screening and checks
- Relocation gate: default to treating relocation as possible (location gate passes) when the profile doesn't say otherwise. But if the profile explicitly states "Willing to relocate: No", that overrides any "open to anywhere" location-preference text — a job that's neither remote, nor in the candidate's current city, nor in their stated desired city/location is not suitable and should fail the location gate (don't add "(able to relocate)" and don't soften this into a pass). Remote jobs always pass regardless of relocation willingness. Count x.5 years as x+1 against a minimum years requirement.
- Score strictly and consistently: skills weigh most (a missing core skill can mean an immediate fail), then experience, then profile and title, education last even when the JD lists a degree.
- cv-pass-check always ends with a clear final result of Pass or Fail at the bottom.
- When screening against a JD, give the assessment only. Don't offer outreach emails, LinkedIn messages or client-facing copy.

## This repo

Local Claude Code rebuild of the `ideal-cv-pipeline-v4` kit (originally built for claude.ai), plus `wideapply-campaign-pipeline`, which chains it with job sourcing and lead-to-todo conversion into a full campaign run. See `PROMPTS.md` for ready-to-send templates for every flow below.

- `ideal-cv-pipeline-v4` — JD + CV → one-page resume → Drive push → leads. `/ideal-cv-pipeline-v4` or "跑一遍 pipeline". Settings: `IDEAL_CANDIDATE`, `AUTO_FIX_ROUNDS`, `PUSH_TO_DRIVE`, `PUSH_LEADS`. (Standalone use only — see next bullet for why `wideapply-campaign-pipeline` turns `PUSH_TO_DRIVE` off.)
- `wideapply-campaign-pipeline` — `campaignId` in → applications sourced → resume per application → finalized against that application → leads converted to connect-todos. Fully automatic past one checkpoint (the sourced-jobs go-ahead). Settings: `TARGET_APPLICATION_COUNT`, `ATTACH_TO_APPLICATION`, `CONVERT_LEADS_TO_TODOS`, `BACKFILL_HANDOFFS`, `MAX_BACKFILL_ROUNDS`.
- **`TARGET_APPLICATION_COUNT` means N finished outcomes, not N sourcing attempts (fixed 2026-10-03).** A real run asking for 3 applications sourced 3, but 2 hit handoff (BIM/AEC domain gap, missing DoD clearance) — gaps `candidate-job-matcher`'s own title/seniority/YOE filters can't see, since they only surface during `ideal-cv-pipeline-v4`'s JD/candidate analysis, after the sourcing slot is already spent. Added Stage 3 (`BACKFILL_HANDOFFS`, default on): when a handoff or thin-JD skip leaves the finished count under target, source exactly that many replacements and run stage 2 on just the new ones, looping up to `MAX_BACKFILL_ROUNDS` (default 3) rounds or until `candidate-job-matcher` reports its search genuinely exhausted. Relies on that skill's existing seen-jobs dedup cache to avoid re-offering the same rejected postings.
- **Resumes go to S3, not Google Drive, for this pipeline (changed 2026-10-02).** `push-resume-to-application` uploads straight to ElasticDash-BE's own S3-backed storage (real multipart, the same path `uploadBuffer`/`controller/general/file.js` already used reliably), replacing the claude.ai Google Drive connector (`mcp__claude_ai_Google_Drive__*`, base64), which hit a reproducible corruption bug (confirmed: one resume silently truncated from 223KB to 18KB, twice) and needed a font-stripped workaround on another run. `wideapply-campaign-pipeline` sets `PUSH_TO_DRIVE = false` on its per-application `ideal-cv-pipeline-v4` calls accordingly — `push-resume-to-drive` is still fine for one-off standalone resume delivery outside this pipeline, just not used here anymore.
- **One resume now produces two separate application documents, split by audience, not just format (settled 2026-10-02).** `wideapply.ApplicationDocuments.kind='cv'` is now specifically the **candidate-facing** file and must be a PDF/image — `wideapply-dashboard`'s `DocumentTab.tsx` only previews those inline, and a `.docx` there renders neither a preview nor a download link (an earlier "two `cv` rows, one per format" design was tried and walked back for exactly this reason: the candidate could end up seeing an empty tab, which defeats the whole point). The new `kind='cv_source'` (migration 058) holds the **admin-only** `.docx` — `applicationDocumentController.js`'s admin upload path (`createWideapplyDocument`) accepts it, `boardController.js`'s candidate-facing query (`getWideapplyApplicationDetailForUser`) explicitly excludes it so it never reaches a candidate's browser at all, and `createWideapplyDocumentForUser` (the candidate's own self-service replace) deliberately does **not** accept it. `drive_review_url` (migration 057, admin-only) defaults to the `.docx`/`cv_source` upload's `fileUrl` if one was given, else the PDF's. Each kind replaces only a document of the same kind — `cv` and `cv_source` never collide.
- `ElasticDash-BE`'s own admin panel (`wideapply-dashboard`, a separate repo) already renders every non-screenshot document (not just one), labeled by kind (`ApplicationDetailAdminModal.tsx`'s `DOCUMENT_KIND_LABEL`), each with a `FilePreviewButton` (preview+download for PDF/image, direct download link otherwise) — added 2026-10-02, since admins need to actually open/verify what got uploaded. The optimistic local-state replace logic in `DocumentTab.tsx`, `ApplicationDrawer.tsx` and the admin modal (`onDocumentReplaced`/`onFileSelected`) matches a prior same-kind document by file format too, not just kind — a holdover from an earlier "two `cv` rows, same kind, different format" design that was walked back (see bullet above), left in place because it's harmless: with one format per kind now, format-aware and kind-only matching behave identically, so there's no reason to churn it back.
- A `wideapply.CampaignApplications` row's resume-related admin field is `drive_review_url` (migration 057), separate from its `wideapply.ApplicationDocuments` files (migration 026/058, see bullet above). Never add `drive_review_url` or a `cv_source` document to `boardController.js`'s candidate-facing path.
- Every ElasticDash-BE write from this repo (`push-wideapply-leads`, `push-wideapply-applications`, `push-resume-to-application`, `convert-wideapply-lead-to-todo`, `convert-wideapply-lead-to-email`, `push-wideapply-resume`) needs a `campaignId`/`applicationId`/`leadId` given by the user — never guessed or looked up — and its own scoped service key under a separate `.secrets/wideapply-*-skill/.env.<env>` (see each skill's "One-time setup"). All six of these skills now live in this repo's own `.claude/skills/`, not globally — run their scripts from the repo root (`node .claude/skills/<skill>/<script>.mjs ...`).
- `convert-wideapply-lead-to-email` (added 2026-10-03) drafts a 3-email Day 0/3/6 outreach sequence from a lead with an email address — approval-gated, never auto-sends. Deliberately **not** wired into `wideapply-campaign-pipeline`'s own stage 2c (the skill file's default stays LinkedIn-only, unlike its LinkedIn sibling) — the automatic wiring is instead opt-in at the prompt layer: `PROMPTS.md` template 9 chains it per eligible lead explicitly, as a deliberate choice for that one named flow, without changing the orchestrator skill or template 7's unchanged behavior. It also requires the target application to already have an `email_sender_id` assigned from its candidate's sender pool — a separate, still entirely manual admin step with no skill of its own yet.
- **A lead's LinkedIn-connect and email-sequence conversions are tracked independently (migration 066, 2026-10-03).** `wideapply.Leads` now has two separate stamp columns — `converted_todo_item_id` (LinkedIn, set by `convertWideapplyLeadToTodo`) and `converted_email_sequence_id` (email, set by `convertWideapplyLeadToEmailSequence`) — where previously both paths shared `converted_todo_item_id` and were mutually exclusive by construction (converting one way blocked the other). This was changed because template 9 below needs a single lead to get BOTH a LinkedIn message and an email sequence for the Manager/`hr_recruiting` tiers; the old shared column made that impossible (the second call always 400'd with "already converted"). Each conversion path now only checks and stamps its own column.
- `wideapply.Leads.tier` gained a 4th value, `hr_recruiting` (migration 066), alongside the original `c_level`/`manager`/`peer` (migration 055) — for HR/Talent-Acquisition/Recruiting contacts. `push-wideapply-leads` validates against all 4.
- `convert-wideapply-lead-to-todo` takes two optional fields now (CLI: `--message`/`--follow-up-message`, body: `message`/`followUpMessage`): `message` (added 2026-10-03) is a pre-drafted LinkedIn connect note saved as the primary to-do's content (sent *with* the connection request); `followUpMessage` (added 2026-10-03) is a pre-drafted note for the chain's own "Send private message to `<name>`" step (sent *after* the connection is accepted — see `createLinkedinConnectionCheckChain` in `adminController.js`). Both threaded through `leadsController.js`'s `convertWideapplyLeadToTodo` and the `/leads/:leadId/convert` route. `PROMPTS.md` template 9 is the first caller that drafts and passes `followUpMessage`; every other caller (templates 1-7, the admin panel) still gets the old empty-content behavior by omitting both.
- `PROMPTS.md` template 9 ("full lead outreach") layers a 20-lead/4-tier composition, a TinyFish company/product research step, per-tier message/email templates, and both-channel conversion (LinkedIn for all 4 tiers, email too for Manager/`hr_recruiting`) on top of template 7 — none of it is any skill's own default, all of it is instructions the prompt itself carries, the same pattern `wideapply-campaign-pipeline` already uses to override `ideal-cv-pipeline-v4`'s defaults for its own stage 2a.
- **`push-wideapply-resume` (added 2026-10-04) closes the "candidate has no parsed resume yet" gap** that blocked every `convert-wideapply-lead-to-email` attempt on real runs (confirmed: 0/8 attempted on a DraftKings run for candidate Agrima Jain, campaign `59a71ceb-4de2-4849-83a0-d4f9a7ce37f0`). `wideapply.Resumes.raw_text` (candidate-scoped, keyed by `ed_user_id`) is a completely separate store from `wideapply.ApplicationDocuments` (per-application, no text-extraction step) — attaching a resume to every application via `push-resume-to-application` never touches it. The skill resolves `edUserId` from the given `campaignId` (`GET /admin/campaigns/:campaignId`), uploads the `.docx` (`POST /resumes/upload`), extracts plain text locally by unzipping `word/document.xml` (no backend text-extraction step exists on this route — don't confuse it with `POST /wideapply/resume/parse`, a stateless onboarding-side LLM extraction that never writes to this table), then `PATCH`es `raw_text`/`parse_status: 'parsed'` onto the row. One-time per candidate, not per application. Verified against the live dev backend 2026-10-04: parsed Agrima Jain's resume (3243 chars), then successfully drafted a real email sequence for a DraftKings manager lead that had previously 400'd with this exact error.
- `.secrets/` is gitignored wholesale (see `.gitignore`) — everything needed to run these skills lives inside this repo, but nothing in that one directory ever gets committed.
- **`candidate-job-matcher-hirebase` (added 2026-10-04) is a Hirebase-backed alternative to the global `candidate-job-matcher` skill** — same seniority/YOE/title-expansion judgment, different job-search provider. Lives in this repo's own `.claude/skills/` (not globally, unlike `candidate-job-matcher`) because Hirebase has no MCP server: a local script, `hirebase-search.mjs`, calls Hirebase's REST API directly, reading `HIREBASE_API_KEY` straight from the repo-root `.env` (not `.secrets/` — this is a read-only external search, not an ElasticDash-BE write). Key differences from the TheirStack version worth remembering: Hirebase parses years-of-experience server-side into a `yoe`/`yoe_range` filter, eliminating candidate-job-matcher's client-side regex pass for the single-dimension case (the multi-dimensional case — e.g. separate dev-years and management-years requirements in one posting — still needs a manual description read, since `yoe_range` is only one parsed range); `geo_locations` takes plain city/region/country strings with no catalog-ID lookup step; and Hirebase has no server-side exclude-by-id or discovered-since filter, so repeat-run dedup is client-side only and costs a credit per re-pulled job (Hirebase bills per job *returned*), unlike TheirStack's `discovered_at_gte` which excluded already-seen jobs before they were ever charged. Neither `push-wideapply-applications` nor `wideapply-campaign-pipeline` have been rewired to use this yet — they still call `candidate-job-matcher` (TheirStack) by name.
