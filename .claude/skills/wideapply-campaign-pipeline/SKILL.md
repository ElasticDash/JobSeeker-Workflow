# WideApply Campaign Pipeline

Given a campaign and a candidate, turns job postings into finished applications: a tailored resume uploaded, hiring-side leads researched, and outreach converted/triggered or queued — this skill never writes the outreach copy itself, that's generated server-side on ElasticDash-BE from each lead's own tier. Two modes choose where the jobs come from and how much outreach happens per lead:

- **`MODE = "source"`** (default): jobs come from a live search (`push-wideapply-applications`, delegating to `candidate-job-matcher-hirebase` or `candidate-job-matcher` per `JOB_SOURCE`, see Settings). Fully automatic once started, the only pause is that skill's own one-time go-ahead on the sourced job table, after that every application runs straight through to leads and connect-todos with no per-resume approval step. See Stage 1 through Stage 3 below.
- **`MODE = "bulk_import"`**: jobs already exist as a markdown file the user hands in (e.g. the output of a GrokBot search run against `candidate-job-matcher-grokbot`'s search condition), not a live search. This mode filters and ranks that list down to a target count, paces the batch at a fixed number of applications per day, and layers full LinkedIn-plus-email outreach drafting onto every lead instead of connect-todos only. See "Mode: bulk_import" below — it replaces Stage 1 with a new Stage 0 and extends Stage 2, Stage 3 stays conceptually the same (top up a shortfall) but draws replacements from the ranked list instead of a new search.

This skill does no resume, sourcing or storage work itself: at each stage, load the named skill with the Skill tool and follow its instructions, except where this file overrides them. For `MODE = "source"`, resumes are generated and stored entirely on ElasticDash-BE (`regenerate-resume` + `generate-resume-files`, see Stage 2a) — never locally, never via `push-resume-to-application`, never via Google Drive (changed 2026-10-06).

## Settings

- `MODE = "source"`: `"source"` (default, Stage 1 through Stage 3 below) or `"bulk_import"` (Stage 0 plus the bulk_import variants of Stage 2/3, see "Mode: bulk_import").
- `JOB_SOURCE = "hirebase"`: which provider `push-wideapply-applications` sources jobs from in `MODE = "source"` (passed straight through as that skill's own `JOB_SOURCE` input). `"hirebase"` delegates to `candidate-job-matcher-hirebase`; `"theirstack"` delegates to `candidate-job-matcher`. Changed to default to Hirebase on 2026-10-04 (was previously hardcoded to TheirStack with no setting at all). Pick one for the whole run and don't switch mid-run — the two providers keep separate seen-jobs dedup caches (see Stage 3), so switching `JOB_SOURCE` between Stage 1 and a Stage 3 backfill round loses the accumulated dedup history and can re-offer jobs already seen under the other provider. Also used by Stage 0's scoring judgment in `bulk_import` mode (step 3 there), though that mode has no live search either way.
- `TARGET_APPLICATION_COUNT`: how many applications should reach a **finished** outcome this run (input 3 below), not just how many get sourced or selected. See `BACKFILL_HANDOFFS` below for why that distinction matters. In `bulk_import` mode this is the size of the plan (e.g. 140), not the size of the raw jobs file, which is normally much larger.
- `ATTACH_TO_APPLICATION = true`: in `MODE = "source"`, run 2a's steps 1-4 (backend `regenerate-resume` + `generate-resume-files`) per application — there is no separate local upload step anymore (`push-resume-to-application` is never called from this pipeline as of 2026-10-06, see 2a/2b). Set false to stop after Stage 1.5 passes without generating a resume at all, e.g. if the `adminEdUserId`/scoped-key setup for those two routes isn't in place yet.
- `CONVERT_LEADS_TO_TODOS = true`: run `convert-wideapply-lead-to-todo` for every lead a given application's run pushed. Set false to leave leads as research and saved rows, no connect-todos. (`bulk_import` mode's `FULL_LEAD_OUTREACH`, below, runs on top of this, not instead of it.)
- `MIN_JOB_DESCRIPTION_CHARS = 200`: an application whose `jobDescription` is shorter than this (or empty) is skipped for stages 2 onward rather than feeding a thin JD into `ideal-cv-pipeline-v4`, JD analysis needs real content to work from.
- `JD_FIT_GATE = true` (added 2026-10-06): run Stage 1.5 (below) on every newly-created application before any Stage 2 work, regardless of which resume-generation path Stage 2a uses. Set false only to restore the old behavior (sourcing-stage gates are the only screen before resume/lead work) — not recommended, see Stage 1.5 for why this gate exists.
- `GENERATE_RESUME = true` (added 2026-10-06): when false, skip 2a/2b entirely for every application that passes Stage 1.5 — no `ideal-cv-pipeline-v4` run, no backend `regenerate-resume`/`generate-resume-files` call, no `push-resume-to-application` upload. Leads still run (see 2a, resume-skipped variant, and 2c) — leads research (`hiring-contact-finder`) and lead conversion need only the application's own company/role/jobDescription, never the candidate's resume content, so dropping resume work doesn't block outreach. Useful when the user only wants leads/outreach for a batch, or when resume generation is being handled some other way outside this run.
- `BACKFILL_HANDOFFS = true`: when an application hits a handoff (stage 4A/6A failure, a genuine JD/candidate mismatch the matcher skill in use (`candidate-job-matcher-hirebase` or `candidate-job-matcher`, per `JOB_SOURCE`) can't catch, since they only check title/seniority/numeric YOE, not domain fit or clearance requirements) or gets skipped for a thin JD, pull in one replacement application for it instead of letting the final finished count fall short of `TARGET_APPLICATION_COUNT`, see Stage 3. Set false to restore the old behavior: select exactly `N` once, report however many of those finish.
- `MAX_BACKFILL_ROUNDS = 3`: hard cap on how many extra backfill rounds Stage 3 runs. Independent of the matcher skill's own internal pull-attempt cap (that one bounds a single search call, this one bounds how many times this skill tops up at the orchestrator level). Hitting this cap with the target still unmet is reported as a shortfall, not retried further, same honesty rule both matcher skills already apply to their own capped stops. **The default of 3 fits a small `TARGET_APPLICATION_COUNT` (single digits to ~20)** — a single days_ago/filter window tends to exhaust after 1-2 rounds (confirmed on a real run: a 14-day window for one title fully exhausted within 2 rounds), so a large `TARGET_APPLICATION_COUNT` (e.g. approaching 140) needs this raised well past 3 — there's no fixed formula, just raise it high enough that "stopped: MAX_BACKFILL_ROUNDS" isn't the reason a large run falls short of a genuinely larger market, and let the matcher skill's own "exhausted" stop reason (not this cap) be what actually ends a maximal-volume run.
- `SOURCE_PARALLELISM = 1` (`MODE = "source"` only): how many applications' Stage 2 (2a/2b/2c) run concurrently, each as its own forked agent, instead of the one-at-a-time loop Stage 2 describes by default. Mirrors `bulk_import` mode's `CV_PARALLELISM` exactly (see "2a/2b/2c, parallelized (source mode)" under Stage 2) — added 2026-10-04 for large-`TARGET_APPLICATION_COUNT` `source`-mode runs, where processing hundreds of applications strictly one at a time would take an impractically long time. Stage 1's own sourcing call stays serial regardless of this setting (one search, even for a large N) — only Stage 2's per-application processing parallelizes.

**`bulk_import`-only settings:**

- `BULK_IMPORT_JOBS_FILE`: path to the raw candidate jobs file (required when `MODE = "bulk_import"`) — either a markdown file (e.g. a GrokBot search run against `candidate-job-matcher-grokbot`'s condition) or the `all_jobs.json` written by `fetch-ats-jobs.mjs` (ATS JSON fetch against `sources.csv`'s Greenhouse/Ashby/Lever/Workday rows). See Stage 0 for the expected shape of each.
- `APPLICATIONS_PER_DAY = 20`: how many selected jobs get carried through CV optimization, upload, and lead outreach per calendar day. This is what paces a 140-job GrokBot batch into roughly a week of daily cohorts instead of running everything in one sitting. **For a `fetch-ats-jobs.mjs`-sourced run, use `4` instead** (changed 2026-10-06) — that source refreshes weekly at a 7-day freshness window and is meant to pace a normal week of applying, not a one-time large batch; see Stage 0 step 5 for the matching start-date default.
- `FULL_LEAD_OUTREACH = true`: for every lead, convert to a connect-todo and trigger the backend's own message generation for its follow-up chain step immediately (`generate-message.mjs`, see `convert-wideapply-lead-to-todo`), and, for Manager/`hr_recruiting`-tier leads that also have an email address and an assigned sender, convert to a Day 0/3/6 email sequence too (backend-generated at conversion time, no separate trigger needed) — same behavior `PROMPTS.md` template 9 already layers over `MODE = "source"`'s default. **Nothing here is drafted by this skill or the orchestrating Claude session (changed 2026-10-05)** — every message and email body comes from ElasticDash-BE's own `leadMessageGenerator.js`/`emailSequenceGenerator.js`, tuned by each lead's `tier`. Set false to fall back to connect-todos only, with no trigger call either.
- `LEAD_BATCH_SIZE = 10`: how many leads get researched, drafted, and converted concurrently per application, matching the concurrency already validated for per-lead outreach calls.
- `CV_PARALLELISM = 5`: how many applications' CV optimization (stage 2a) run concurrently within one day's batch, each as its own forked agent. Keep this bounded rather than running a full day's 20 at once by default, raise it only once you've confirmed the environment (API rate limits, ElasticDash-BE write volume) can sustain more concurrent `ideal-cv-pipeline-v4` runs.

## Inputs

1. **`campaignId`** (required) — never guessed, same rule as every skill this chains.
2. **Candidate profile** (required) — same shape `candidate-job-matcher`/`candidate-job-matcher-hirebase` need (title history, YOE, location preference, work auth, desired salary).
3. **Target job count `N`** (required) — ask if unstated. In `MODE = "bulk_import"`, this is how many of the parsed jobs to carry all the way through the pipeline (filtering happens in Stage 0), not a sourcing count.
4. **Original CV template** (.docx, required) — candidate material and the layout `ideal-cv-pipeline-v4` stage 7 needs.
5. **Contact set 1 / Contact set 2** (optional) — passed through to every per-application `ideal-cv-pipeline-v4` run unchanged; see that skill's own contact-set rules. These are application-submission identities, not the candidate's own contact — supplying one is what makes 2b produce a separate admin-only Application `.docx` instead of reusing the candidate-facing Original for both roles.
6. **Environment** (optional, default `dev`) — `dev` or `prod`, passed to every scoped-key skill this chains. Before the *first* prod write in a run, confirm explicitly with the user even if they already said prod once.
7. **`BULK_IMPORT_JOBS_FILE`** (required only when `MODE = "bulk_import"`) — the markdown file of raw jobs, see Stage 0.

## Working files

Use a run folder, e.g. `wideapply-campaign/<campaignId>-<date>/`, so runs don't overwrite each other.

- `00_bulk_jobs.md` (`bulk_import` only): every job parsed from `BULK_IMPORT_JOBS_FILE`, with its fit score, keep/drop decision, rank, assigned `apply_date`, and processing status, see Stage 0.
- `01_applications.md`: every application logged this run (id, company, role, jobDescription, jobPostUrl, status), from `push-wideapply-applications` in `MODE = "source"`, or mapped directly from `00_bulk_jobs.md` in `MODE = "bulk_import"`.
- `<company>-<role>/`: one subfolder per application, holding that application's own `ideal-cv-pipeline-v4` working files (`00_contact.md` through `09_leads.md`; no `08_drive.md` here since `PUSH_TO_DRIVE` is off for this pipeline), plus (`bulk_import` only) `10_outreach.md` recording each lead's conversion/trigger outcome and tier (the message/email content itself lives on the backend's to-do rows, not drafted or duplicated into this file).
- `02_results.md`: the per-application summary this skill appends to as each application finishes (see Output)

## Mode: source (default)

Stages 1 through 3 below run only when `MODE = "source"`. For `MODE = "bulk_import"`, skip straight to "Mode: bulk_import" further down, it replaces Stage 1 with its own Stage 0 and continues into Stage 2/3 with the variants noted there.

## Stage 1: Source applications (round 1)

Run `push-wideapply-applications` with `campaignId`, the candidate profile, `N`, `JOB_SOURCE`, and the environment. Follow that skill's own flow exactly, including its Step 3 mapped-table-then-go-ahead — this is the one human checkpoint in the run, and it covers the whole batch at once, not one approval per job. (A later Stage-3 backfill round, if one runs, reuses this same go-ahead flow and must pass the same `JOB_SOURCE` — see Stage 3.)

Append the created applications to `01_applications.md`: id, company, role, jobDescription, jobPostUrl, status. If `push-wideapply-applications` logged fewer than `N` in this round (shortfall reported by the matcher skill in use — e.g. the search itself is exhausted, not just this round's pull cap), note it, but don't treat it as fatal yet — Stage 3 below is a second chance to close the gap, and if the shortfall is because the search is genuinely exhausted, Stage 3 will discover that too and stop rather than loop pointlessly.

## Stage 1.5: JD-fit gate

**Both modes, added 2026-10-06.** Runs on every newly-created application (Stage 1's round, every Stage 3 backfill round, and `bulk_import`'s Stage 0 kept rows) before any Stage 2 work, when `JD_FIT_GATE` is true.

The reason this exists: the sourcing-stage checks (title, seniority, numeric YOE floor/ceiling, stack-match, national-security) are deliberately coarse — stack-match in particular gates only on core implementation language, never on framework or platform depth, since "a different framework in a language the candidate already has is not a real gap" (see `candidate-job-matcher-hirebase`'s own stack-match reasoning). That leaves a real, separate gap: a posting can state a named framework (e.g. Spring Boot), a specific cloud platform with production-years attached (e.g. "5+ years hands-on production experience with AWS/Azure/GCP, including Kubernetes"), or a skill-*composition*-specific years requirement (e.g. "7+ years of **full-stack** experience" — a narrower, harder bar than the candidate's total YOE) as a hard, explicit requirement the candidate has zero profile evidence for, and nothing before Stage 2 would catch it.

This used to be caught incidentally by `ideal-cv-pipeline-v4`'s own stage 2a JD analysis (the same mechanism Stage 3 below already backfills around for domain/clearance mismatches). But that analysis doesn't run at all when Stage 2a uses a non-local resume-generation path (e.g. calling ElasticDash-BE's own `regenerate-resume`/`generate-resume-files` instead of `ideal-cv-pipeline-v4` — see Stage 2a's own note on this) — so skipping local generation also silently drops this check, with no replacement. Confirmed on a real run (candidate Mark Matas, campaign `a1becd1b-a22b-4b6e-808b-04f131d848ac`, 2026-10-06): two sourced-and-logged applications (Accenture, Allstate) both had an explicit hard-stated cloud-platform + Kubernetes requirement with zero evidence in the candidate's profile, and would have gone through resume/lead work with no handoff signal at all under the backend-generation path. A systemic sweep of the rest of that same sourcing round found 9 more of the same pattern (Spring Boot, AWS-specific services, Azure, full-stack-years composition) that the sourcing-stage gates had already let through.

**How to run it:** for each application, read its `jobDescription` against the candidate's profile and flag any requirement that is (a) stated as a hard, numbered/explicit minimum — not "preferred," "a plus," "not required," or one option in an explicit "one or more of" / "or equivalent" list — and (b) a named technology, platform, or skill-composition the candidate's profile shows zero real evidence for. A single such hard-and-unmet requirement is enough to fail the gate (elimination-tier, same severity class as a missing core skill in `cv-pass-check`'s own scoring — see CLAUDE.md's "Score strictly and consistently"). Soft/OR'd/"preferred" mentions of the same technologies are not grounds to fail. This is a pass/fail screen only — it does not score or rank, and it is not a substitute for `ideal-cv-pipeline-v4`'s full JD analysis when that pipeline *is* used (running both is harmless but redundant).

**A JD can mention the same technology more than once with different framing — check every occurrence independently, don't stop at the first one** (confirmed missed on a real run, candidate Tarunn Gusain, 2026-10-07: Nielsen's FDE posting mentioned AWS four times — three softly, "Google or AWS," "AWS Bedrock Agents... preferred," "via AWS Bedrock, Google Cloud Vertex AI, Microsoft Azure AI/Foundry, etc." — and the gate correctly read those as OR'd/soft and safe against the candidate's GCP-only profile. But a separate bullet buried in the middle, "AWS ecosystem with specific, practical experience leveraging AWS Cognito for identity management, user authentication, and secure API access control," had no OR and no "preferred" — a hard, standalone requirement for a named AWS service the candidate had zero evidence of. It was missed because the other three AWS mentions were checked, found safe, and the posting was marked clear without separately verifying every remaining mention of the same keyword). Before passing a posting, search the full `jobDescription` for every instance of each named technology/platform it references (not just the first match, not just the one in an obvious "Requirements" section header) and classify each occurrence's framing on its own — one OR'd mention elsewhere in the same document does not clear a different, hard-framed mention of the same technology.

**Backstop location/work-authorization re-check, same stage:** also read the posting's own full location list (not just the `city`/`workMode` fields already mapped onto the application — read the raw posting data's locations array or location text) against the candidate's actual work authorization/location preference, even though Stage 1's sourcing search was already scoped to the right geography. Confirmed on the same 2026-10-06 run: a posting returned by a `geo_locations: [{"country": "United States"}]`-scoped Hirebase search turned out to list only Canadian locations (Alberta, British Columbia, Saskatchewan, Quebec, Ontario) with no US location at all — the provider's geo filter isn't airtight. Fail the gate the same way for a country/authorization mismatch as for a framework/platform gap.

**On fail:** treat exactly like a Stage 2a handoff — record "JD-fit gate: <unmet requirement>" in `02_results.md`, do not run any Stage 2 work for this application, leave it as `found` on the backend (never delete it), and let `BACKFILL_HANDOFFS`/Stage 3 count it toward the shortfall same as any other handoff. If an application already had Stage 2 work started before a fit issue is noticed (e.g. caught late, or `JD_FIT_GATE` was added mid-run), stop any further Stage 2 work on it and record it as a handoff from that point rather than reversing what's already been pushed.

**On pass:** continue to Stage 2 as normal.

## Stage 2: Per application

Shared by both modes, with `bulk_import` running 2a concurrently across a day's batch and replacing 2c, see "Mode: bulk_import" below for those variants, read this stage first either way.

For each application in `01_applications.md`, in order — unless `SOURCE_PARALLELISM > 1` and `MODE = "source"`, see "2a/2b/2c, parallelized (source mode)" below, which replaces this one-at-a-time loop with a concurrent one; the per-application steps themselves (2a/2b/2c) are identical either way, only how many run at once differs.

**Skip condition:** if `jobDescription` is missing or shorter than `MIN_JOB_DESCRIPTION_CHARS`, skip stages 2a–2c for this application. Record it in `02_results.md` as "skipped: no usable job description" and move to the next one. Do not fetch `jobPostUrl` or otherwise invent JD content to work around this. Like a handoff, this counts as "needs a replacement" for Stage 3 when `BACKFILL_HANDOFFS` is on.

### 2a. Resume and leads

**`GENERATE_RESUME = false`: skip resume entirely, leads only.** Do not run `ideal-cv-pipeline-v4`, do not call the backend's `regenerate-resume`/`generate-resume-files`, and skip 2b entirely (no `push-resume-to-application` call — there's no file to attach). Instead:
1. Run `hiring-contact-finder` directly for this application's `company` + `role`, using the application's own `companySize` (if set) for headcount and `jobPostUrl`'s domain or the application's `companyType` for disambiguation if the company name is generic — no candidate profile or resume input needed, this skill never reads either.
2. Run `push-wideapply-leads` with `campaignId` and this application's id to insert the returned leads.
3. Continue straight to 2c below with whatever lead `ids` came back — 2c's own logic (convert to connect-todos, trigger backend message generation, email for eligible tiers) is unchanged either way; it was never resume-dependent.

Record the leads-found count and push result in `02_results.md` the same as the full path would. Skip the rest of this section (`GENERATE_RESUME = true`, the default) when running this variant.

**`GENERATE_RESUME = true` (default) — backend-generated only, never local (changed 2026-10-06, user directive).** `ideal-cv-pipeline-v4` is no longer called from this pipeline at all — no local JD analysis, no `ideal-candidate-2026-09-27` rewrite, no `cv-pass-check`/humanize/`cv-file-generator-2026-09-29` build. That entire local-drafting path now only matters for `ideal-cv-pipeline-v4`'s own standalone use (see CLAUDE.md), not for any application this pipeline touches. Instead:
1. `POST /admin/campaigns/:campaignId/applications/:applicationId/regenerate-resume`, body `{ adminEdUserId }`. Responds as soon as generation is marked `'generating'` — the actual LLM call runs server-side in the background, this call does not wait for it.
2. Poll `GET /admin/campaigns/:campaignId/applications/:applicationId` until `tailored_resume_status` leaves `'generating'` (succeeds, or lands in `'error'` with `tailored_resume_error` set). Use a short backoff between polls — this is a background LLM call, not an instant operation.
3. On `'error'`: retry step 1 once; a second failure is a handoff-equivalent ("resume generation failed: <tailored_resume_error>" in `02_results.md`), do not run leads/2c for it.
4. On success: `POST /admin/campaigns/:campaignId/applications/:applicationId/generate-resume-files`, body `{ adminEdUserId }` — this renders `tailored_resume_text` into the `.docx`/`.pdf` pair and attaches them directly as the application's `cv_source`/`cv` documents server-side. **This replaces 2b entirely** — there is no local file to render, convert, or upload, so `push-resume-to-application` is never called from this pipeline either (see 2b below).
5. Run `hiring-contact-finder` for leads the same as always — resume generation and lead-finding are independent, this isn't gated on step 4 landing first.

**`regenerate-resume`/`generate-resume-files` only rewrite `profileSummary`/bullets** (header, education, skills stay exactly as the candidate's own profile/latest-parsed-resume has them) and run no JD/candidate fit analysis of their own — which is exactly why Stage 1.5 above exists and must still run before step 1, every time, regardless of this change.

**`adminEdUserId` and the scoped key for these three routes**: not yet set up as of 2026-10-06 — no script in this repo calls `regenerate-resume`/`generate-resume-files`/the polling `GET` yet. Building that script (same `.mjs` + scoped-key pattern as `push-resume-to-application`, but for these three admin routes instead) is a prerequisite before this stage can actually run, not something to skip past. Don't guess an `adminEdUserId` — resolve it the same way any other admin-scoped write in this repo does (ask, or read it off an existing admin-authenticated call) before this script exists.

**On a resume-generation failure after the one retry** (step 3 above): stop at stage 2a for this application only. Record "handoff: resume generation failed: <error>" in `02_results.md`, do not run 2c for it, and continue the loop with the next application. One application failing never stops the batch — and if `BACKFILL_HANDOFFS` is on, it doesn't shrink the final finished count either (see Stage 3).

**On success:** record in `02_results.md`:
- the `cv`/`cv_source` document `fileUrl`s `generate-resume-files` returned
- `09_leads.md`'s push result — the inserted lead `ids`, or the reason none were pushed (the relevant reason here is the "no live application" 400, which should not occur since this application was just created — if it does anyway, record it as-is rather than retrying)

### 2b. Finalize against the application

**Removed (2026-10-06) — always skipped now, not just when `GENERATE_RESUME = false`.** This stage used to render the drafted `.docx` to PDF locally and call `push-resume-to-application` to upload both files. Now that 2a's step 4 (`generate-resume-files`) attaches the `cv`/`cv_source` documents directly on the backend, there is no local file left to render, convert, or upload — `push-resume-to-application` is never called from this pipeline. `ATTACH_TO_APPLICATION` is retained as a setting (see Settings above) but now only gates whether 2a runs steps 1-4 at all, there's nothing left in a separate "2b" to gate. This section is kept as a placeholder so the stage numbering in `02_results.md`/past run folders doesn't shift under old records — go straight to 2c.

### 2c. Connect-todos for this application's leads

**`MODE = "source"` only** — in `bulk_import` mode, this step is replaced by "Mode: bulk_import"'s own 2c (full lead outreach), skip this version entirely there.

If `CONVERT_LEADS_TO_TODOS` is true and 2a's `09_leads.md` push result has any `ids`: for each lead id, run `convert-wideapply-lead-to-todo` with `campaignId`, that `leadId`, and `applicationId` set explicitly to this application's id (known already, so there's no ambiguity to resolve) — no `--message`, this skill never drafts the connect note. Immediately follow each successful conversion with that skill's `generate-message.mjs` for the same lead, so the backend drafts the chain's follow-up message right away instead of waiting on the candidate's own accept-confirmation. Record each lead's outcome (todoId, whether the trigger succeeded, or the error, e.g. "already converted" is not a failure to flag, just note it) in `02_results.md`.

If 2a found leads but didn't push any (no `ids`), skip 2c for this application and say why in `02_results.md` (should not normally happen here, since `ideal-cv-pipeline-v4` already has this exact `campaignId`).

### 2a/2b/2c, parallelized (source mode)

**`MODE = "source"` and `SOURCE_PARALLELISM > 1` only** (added 2026-10-04) — replaces the one-at-a-time loop above with the concurrent pattern `bulk_import` mode's own "2a, parallelized" already uses, extended to cover 2c as well since source mode's 2c (connect-todos, not full outreach) is cheap enough to run inside the same forked agent rather than as a separate batched pass.

Run 2a, 2b, and 2c for up to `SOURCE_PARALLELISM` applications at once, each as its own forked agent (the Agent tool, `subagent_type: "fork"`). Each forked agent handles one application end to end (resume drafted and checked, rendered to PDF, both files uploaded, leads researched and pushed, leads converted to connect-todos) and reports back a `02_results.md`-shaped summary for its application; start the next queued application from `01_applications.md` the moment a slot frees up, rather than waiting for the whole batch to finish. The orchestrating agent (you) collects each report and appends it to the real `02_results.md` as it arrives — don't let a slow application hold up recording the fast ones.

Keep `SOURCE_PARALLELISM` bounded to what the environment can actually sustain (ElasticDash-BE write volume, Hirebase/TinyFish/Apollo rate limits, LLM concurrency) — there's no single safe default across every campaign size the way `bulk_import`'s `CV_PARALLELISM = 5` assumes a day-sized batch; pick a value and watch the first batch's error rate before trusting a higher one on a large run.

A handoff or thin-JD skip inside one forked agent is recorded exactly as the serial version describes (stop at 2a for that application, don't run 2b/2c for it, don't let it block any other concurrently-running application) — Stage 3 below still runs afterward against the accumulated `02_results.md`, unchanged by parallelism.

## Stage 3: Backfill handoffs and thin-JD skips

**`MODE = "source"` only** — see "Mode: bulk_import" below for that mode's own backfill variant, which draws from the ranked reserve pool instead of a live search.

Skip this stage entirely if `BACKFILL_HANDOFFS` is false, or if every application from Stage 1/the prior backfill round finished (no handoffs, no thin-JD skips, no Stage 1.5 JD-fit-gate failures) — most runs never reach this stage at all.

The reason this exists: the matcher skill in use (`candidate-job-matcher-hirebase` or `candidate-job-matcher`, per `JOB_SOURCE`)'s own filters (title, seniority, numeric YOE) run *before* a job is logged as an application, and they cannot see a domain-fit gap ("requires BIM/Revit/AEC experience"), a hard credential gate ("requires an active DoD Secret clearance"), or a framework/platform-depth gap (Stage 1.5) — those are only discovered later, inside `ideal-cv-pipeline-v4`'s own JD/candidate analysis (stage 2a above) or Stage 1.5's JD-fit gate. By the time a handoff or Stage 1.5 failure happens, that slot has already been "spent" against `N`. Without this stage, asking for `N` applications silently means "up to `N` attempts," not "`N` real outcomes" — this stage is what makes it the latter.

Loop, starting at round = 2:

1. **Count finished applications** across every round so far in `02_results.md` (reached 2a/2b/2c successfully — not a handoff, not skipped, not a Stage 1.5 JD-fit-gate failure). If this count >= `TARGET_APPLICATION_COUNT`, stop — target met, move to Output.
2. **Stop conditions, checked before sourcing anything this round:**
   - `round - 1 > MAX_BACKFILL_ROUNDS` (i.e. this would be backfill round `MAX_BACKFILL_ROUNDS + 1`) — stop, target not fully met, carry the shortfall into Output.
   - The prior round's Stage 1 call reported the search itself as exhausted (not just this round's own pull-cap, see the matcher skill's own stop-reason wording) — stop immediately rather than re-running a search that has nothing left to give. Carry the shortfall into Output.
3. **Source replacements**: run Stage 1 again with `N' = TARGET_APPLICATION_COUNT - (finished count from step 1)` — only as many as are still needed, not a fresh `TARGET_APPLICATION_COUNT`, and the same `JOB_SOURCE` as round 1 (never switch provider mid-run, see Settings). The matcher skill's own seen-jobs dedup cache (keyed by this candidate, carried automatically across calls within this run, separate per provider) already excludes every job shown in every earlier round, including the ones that became handoffs, so this naturally searches forward into new postings rather than re-offering the same rejected ones. Append the new applications to `01_applications.md`, continuing the same go-ahead flow as round 1.
4. **Run Stage 2 on only the newly sourced applications** from this round (not the whole file again) — append their outcomes to `02_results.md`.
5. Increment round, go back to step 1.

A company that produced a handoff once (e.g. Power Design's domain mismatch) may appear again in a later round via a *different* posting at the same company — that's not a bug to special-case here; if it happens, it just consumes another handoff slot and another backfill round like any other, bounded by the same `MAX_BACKFILL_ROUNDS` cap.

## Output (`MODE = "source"`)

Reply in the user's language. No em dashes.

1. A one-line summary: applications sourced across all rounds (N requested **finished** vs. how many actually finished, noting any shortfall and whether it's because `MAX_BACKFILL_ROUNDS` was exhausted or the search itself ran out), how many hit handoff in total, how many failed the Stage 1.5 JD-fit gate, how many were skipped for a thin JD in total. If Stage 3 ran, say how many rounds it took.
2. A table from `02_results.md`, one row per application across every round: company / role / CV pipeline result / attach status (incl. the S3 `fileUrl`) / leads found / leads converted to todos.
3. Every handoff's reason, every Stage 1.5 JD-fit-gate failure's unmet requirement, and every application skipped for a thin JD, listed explicitly (not just counted) so nothing silently falls through — including ones later replaced by Stage 3, so the user can see what got filtered and why.
4. Any scoped-key setup still missing (e.g. `push-resume-to-application` or `convert-wideapply-lead-to-todo`'s one-time setup not done yet) — report it once per skill, don't repeat it per application.

Give the summary and the table only. Do not offer to write outreach emails, LinkedIn messages or client-facing copy. Do not recap the stages.

## Mode: bulk_import

Everything below replaces Stage 1 with Stage 0, and replaces Stage 2's 2c and Stage 3 with the variants here. Stage 2's 2a/2b still apply as written above, just run the way "2a, parallelized" below describes instead of one application at a time.

### Stage 0: Parse, filter, rank, and schedule the job list

Run once per run folder. If `00_bulk_jobs.md` already exists for this run folder, skip straight to "Day-batch execution" below instead of re-parsing, this stage is idempotent by design so a daily continuation run doesn't redo it.

1. **Parse `BULK_IMPORT_JOBS_FILE`.** Two known shapes:
   - **Markdown** (a GrokBot search run, or any hand-assembled file): the shape isn't fixed (a table or repeated per-job sections), so read it structurally rather than assuming one format: extract, per job, at minimum a title, a company, and a job description or posting text long enough to analyze. A posting URL and a source board (useful for the tier weighting below) are expected but not required.
   - **`fetch-ats-jobs.mjs`'s `all_jobs.json`**: a flat JSON array, each entry already normalized — `company`, `platform` (`greenhouse`/`ashby`/`lever`/`workday`), `title`, `location`, `postedAt` (ISO date), `url`, `descriptionHtml`, plus a platform-specific `sourceId`. Map directly: `title`→title, `company`→company, `url`→posting URL, `descriptionHtml`→job description text, `platform` stands in for "source board" in the ranking step below (no separate board-tier table applies here — it isn't one of `candidate-job-matcher-grokbot`'s board tiers, treat every platform as equal rank weight). No structural guessing needed, the fields are already named.

   Either way: any entry missing a usable title, company, or a job description at or above `MIN_JOB_DESCRIPTION_CHARS` is dropped at this step and counted (not silently discarded, not fetched or invented), note the drop reason.
2. **Dedup** against `01_applications.md` from any prior run in this same campaign (by company plus role, or by posting URL if present), and against this run's own `00_bulk_jobs.md` if Stage 0 is somehow re-run, so the same posting never gets scheduled twice.
3. **Score and filter**, applying the matcher skill in use (`candidate-job-matcher-hirebase` or `candidate-job-matcher`, per `JOB_SOURCE`)'s own judgment (read that skill's Step 1/Step 2/Step 4 if you haven't already): compute the candidate's seniority and YOE from the profile (floor is `candidate_YOE - 1`, capped at 4 once `candidate_YOE` is 6 or more, ceiling is `candidate_YOE`, see CLAUDE.md's "YOE floor, capped"), drop postings whose title or stated minimum years signal a level outside the candidate's bucket (both directions, too senior and too junior), drop postings the relocation gate rules out (CLAUDE.md's Screening and checks section, same "Willing to relocate: No" handling both matcher skills and `push-wideapply-applications` already apply), and separately drop any posting whose JD explicitly excludes hiring in the candidate's current state or region for state-tax or similar reasons, even for an otherwise-remote role, that's an employer-side hard exclusion distinct from the candidate's own relocation preference, not a soft flag to carry forward. Rank what's left, best fit first, factoring in title closeness to the targeted title, tightness of the YOE match, keyword/stack overlap with the candidate's Skills list, and the job board's tier if known (`candidate-job-matcher-grokbot`'s tiers: startup boards and mixed boards rank above a general board like Indeed, all else equal). This step ranks and drops on title/seniority/YOE/location only — it does not catch a framework/platform-depth gap (named technology stated as a hard requirement with zero profile evidence); Stage 1.5's JD-fit gate still runs on every `keep: true` row once it's logged as an application, same as `MODE = "source"`.
4. **Keep a reserve beyond `TARGET_APPLICATION_COUNT`.** Don't drop everything past rank N, since there's no live search to fall back on later the way `MODE = "source"`'s Stage 3 has, keep the next 20 to 30 percent ranked below the cutoff as a backfill reserve for this run's own Stage 3 variant below. Mark the top N `keep: true`, the reserve `keep: reserve`, everything else `keep: false` (too far down to be worth holding).
5. **Assign `apply_date`.** Starting from today (or an explicit start date the user gave), assign the top `APPLICATIONS_PER_DAY` kept jobs to day 1, the next `APPLICATIONS_PER_DAY` to day 2, and so on, best-ranked jobs get the earliest dates — calendar days, including weekends, same as before. **For a `fetch-ats-jobs.mjs`-sourced run specifically, two defaults change instead of this general rule** (added 2026-10-06, scoped to that source only — don't apply either default to a markdown/GrokBot-sourced run unless the user asks): start the schedule on the coming Monday (the first day of the calendar week *after* the current one, not today — that source's weekly 7-day freshness window means today's fetch belongs to next week's application push, not whatever's left of this week), and assign only to weekdays, Monday through Friday, skipping Saturday/Sunday. At the default `APPLICATIONS_PER_DAY = 4` for this source, that's 4 a day across those 5 weekdays, 20 for the week; a smaller kept count just leaves the later weekdays with fewer or none. Either default is overridden by an explicit start date or day-of-week instruction the user gives for that run. Reserve-pool jobs get no `apply_date` yet, one gets assigned only when it's pulled in by Stage 3 below.
6. **Write `00_bulk_jobs.md`**: one row per parsed job, columns `rank`, `title`, `company`, `jobPostUrl`, `source board`, `keep` (`true`/`reserve`/`false`), `apply_date` (blank until assigned), `status` (`pending`/`processing`/`done`/`handoff`/`skipped`). Show this table to the user as a go-ahead checkpoint before creating any applications, same role Stage 1's mapped table plays in `MODE = "source"`, this is the one pause in `bulk_import` mode too.
7. **Log the kept jobs as applications.** Map every `keep: true` row to the same application JSON shape `push-wideapply-applications`'s own Step 3 table defines (company, role, status `'found'`, jobPostUrl, jobDescription normalized to clean markdown per that skill's own rules, city/workMode/salaryRange only if honestly known, `source` set to the board name or `'bulk_import'` if unknown) and call `push-applications.mjs` directly (same script, same calling convention as that skill's Step 4), there's no live search to run here so `push-wideapply-applications`'s own Step 1/Step 2 don't apply, only its Step 3 mapping and Step 4 script call do.
   - **Markdown/GrokBot source**: use that skill's TheirStack or Hirebase mapping table, whichever matches each job's `source` board, or map by hand if the board isn't either (company/role/jobPostUrl straight from the row, `source` set to the board name).
   - **`fetch-ats-jobs.mjs` source**: `company`←`company`, `role`←`title`, `jobPostUrl`←`url`, `jobDescription`←`descriptionHtml` normalized to clean markdown per `push-wideapply-applications`'s own normalization rules (strip the HTML tags Greenhouse/Ashby/Lever/Workday return, don't pass raw HTML through), `city`←parsed from `location` only if it cleanly names one (omit rather than guess), `workMode`←`remote` if `location` or the description plainly says fully remote, else omit, `source`←`"ATS fetch (" + platform + ")"` e.g. `"ATS fetch (Greenhouse)"`. No salary/companyType/companySize data exists on this source, leave those fields unset.

   Append results to `01_applications.md` as usual.

### Day-batch execution

Each invocation (whether the first run or a scheduled daily continuation) processes exactly one day's batch, then stops:

1. Find the earliest `apply_date` in `00_bulk_jobs.md` that still has any `status: pending` rows (not necessarily literally today, in case a scheduled run was missed, process the oldest unprocessed batch first rather than skipping ahead).
2. Run Stage 2 (2a, 2b, this mode's own 2c below) on every `pending` row for that date, batched `CV_PARALLELISM` at a time via forked agents for 2a, see "2a, parallelized" below.
3. Mark each processed row `done`, `handoff`, or `skipped` in `00_bulk_jobs.md` as it finishes, matching the same outcomes Stage 2 already defines.
4. Run this mode's Stage 3 variant (below) if any row from this batch became a handoff or thin-JD skip and `BACKFILL_HANDOFFS` is true.
5. Stop. Report this day's batch in Output (below). To actually realize the day-by-day pacing without the user manually re-invoking this skill every day, use the `schedule` skill to set up a daily cron that re-invokes this same run folder in `bulk_import` mode, each invocation naturally picks up the next unprocessed day's batch per step 1 and exits when done, rather than looping across days inside one conversation.

**Leads and their connect-todos/email sequences are distributed by date the same way, as a side effect of this day-batch structure, not a separate date field.** Neither `wideapply.Leads` nor the to-do/chain tables have a scheduled-date column to set — a lead's to-do and email sequence simply get created with whatever real timestamp it has when 2c actually runs for it, and 2c only runs for a given application once that application's `apply_date` batch is reached in step 1 above. So pointing `APPLICATIONS_PER_DAY`/the start-date default at a real week (via the `schedule` cron, not by running every day's batch back-to-back in one sitting) is what makes a Monday application's leads land Monday and a Tuesday application's leads land Tuesday — running every batch immediately in one sitting would create every lead/to-do on the same day regardless of `apply_date`, defeating the point.

### 2a, parallelized

Within one day's batch, run 2a (resume and leads via `ideal-cv-pipeline-v4`) for up to `CV_PARALLELISM` applications at once, each as its own forked agent (the Agent tool, `subagent_type: "fork"`), rather than the single-application-at-a-time loop `MODE = "source"` uses. Each forked agent handles 2a and 2b for its own application end to end (resume drafted, rendered to PDF, uploaded), then reports back; start the next queued application the moment a slot frees up rather than waiting for the whole batch to finish before starting any 2c. Keep `CV_PARALLELISM` bounded (default 5) so a 20-job day doesn't fire 20 concurrent `ideal-cv-pipeline-v4` runs against the same ElasticDash-BE environment and the same LLM rate limits.

### Stage 3 (bulk_import variant): backfill from the ranked reserve

4. Run Stage 2 on just this replacement when its `apply_date` batch is processed (it may land in the current batch or a later one, depending on step 2's date).
5. If the reserve pool itself runs out before `MAX_BACKFILL_ROUNDS` worth of replacements are found, or `MAX_BACKFILL_ROUNDS` is hit first, stop and report the shortfall, same honesty rule as the source-mode variant, don't go back to `BULK_IMPORT_JOBS_FILE` looking for more, that file is a fixed input for this run.
